# DECISIONS — QData 데모가 지금 모습인 이유

> 형식: 맥락 / 결정 / 왜 / 결과(깨면 안 되는 것). 코드가 '무엇'을 보여준다면 이 문서는 '왜'를 남긴다.

## ADR-1. 제품은 중립, 발주처는 '적용 사례' 팩으로
- **맥락**: 사용자 지시 — "QData 서비스 자체는 중립으로 표현되고, 그 서비스를 활용해 한국도로공사에 무엇을 제공할지를 보여줘야 한다."
- **결정**: 기본 화면(standard 팩)은 발주처명 없는 '샘플 사업장'. 한국도로공사는 전환 가능한 적용 사례(expressway 팩).
- **왜**: 같은 콘솔이 제품 소개(중립)와 발주처 제안(적용) 두 용도를 동시에 증명한다 — 제안서 2장(제품)과 3장(적용)의 화면 근거가 한 데모에서 나온다.
- **결과**: `DOMAIN_LIST[0]`은 반드시 standard(`check:domains`가 강제). 중립 화면에 발주처 용어가 한 건이라도 나오면 결함(`verify.mjs` 금칙어).

## ADR-2. 메뉴 = 제품 페이지 흐름
- **결정**: 콘솔 메뉴를 제품 페이지 순서(개요 → 수집·연계 → 코어 파이프라인 → AI 데이터 엔진 → 거버넌스 → 운영 → 활용)로 구성.
- **왜**: 제안서·영업 현장에서 "페이지에 있던 그 기능이 어디 있나"에 메뉴 이름만으로 답하게. 원문 대응표는 `docs/SOURCE-QDATA.md` §3.
- **결과**: 원문에 없는 메뉴를 추가하려면 먼저 이 흐름의 어느 단계인지 정하고 SOURCE §3에 대응을 적는다.

## ADR-3. 재사용 10 + 신규 7
- **맥락**: 포크 원본(RoadQ) 관리자 61메뉴 중 상당수가 이미 QData 기능 그 자체였다(RAG 파이프라인 5탭 = 제품 5대 기능 중 4개, 지식 증강 전략 = RAG/CAG/TAG, 카탈로그·계보 등).
- **결정**: 그런 화면은 재사용(10), 원문에 있는데 없던 것 — 5계층 개요·소스/엣지·6단계 보드·표준화·산출물·품질 규칙·서비스 연계 — 은 신규(7). AgentQ 성격 메뉴(GPU·LLM 학습·에이전트 빌더·사용자 관리 등)와 사용자 포털은 제거.
- **결과**: 두 콘텐츠 경로가 공존한다 — 신규는 팩 `qdata`(getQdata), 재사용은 `mocks.js` + 팩 `adminContent`. 새 화면은 신규 경로로 만든다.

## ADR-4. qdata는 섹션 단위 폴백
- **결정**: `getQdata(domain)`는 팩이 생략한 섹션을 표준 데모 섹션으로 채운다.
- **왜**: 새 적용 사례를 점진적으로 채워도 화면이 깨지지 않게.
- **위험과 대응**: 폴백은 '중립 콘텐츠 노출'이다. 그래서 `check:domains`가 누락 섹션을 실패로 보고, `verify.mjs`는 적용 사례 화면에서 표준 전용 말(샘플 사업장·김지원)을 금칙어로 잡는다 — 조용한 폴백 방지.

## ADR-5. 브랜드 토큰은 제품 페이지 실측값
- **결정**: `index.css` `@theme`의 `qd-*` 토큰(`#0075DE` 등)만 쓴다. 상태색(정상·주의·위반)만 의미색.
- **왜**: 데모가 제품 페이지와 같은 제품으로 보여야 한다.

## ADR-6. 서비스워커 캐시는 앱 접두어로만 정리
- **맥락**: github.io는 여러 데모(RoadQ·AgentQ·QData)가 같은 오리진을 쓴다. 포크 원본 SW는 활성화 시 "자기 이름이 아닌 캐시를 전부 삭제"해 이웃 데모의 오프라인 셸까지 지운다.
- **결정**: 캐시 이름 `qdata-shell-v*`, 정리 대상도 같은 접두어만.

## ADR-7. 포크 + 새 git 이력
- **결정**: RoadQ에서 포크하되 이력은 새로 시작. 백엔드 없음·시뮬레이션 정직성·ASCII 빌드 판정·CI 이중 배포 등 운영 원칙은 승계.
